# Состояние и данные

## Чем props отличаются от state?

Props — входные данные компонента, приходят сверху и компоненту принадлежать не могут (read-only). State — приватные данные компонента, которые он сам создаёт и меняет.

```tsx
function Parent() {
  const [count, setCount] = useState(0);
  return <Child count={count} onInc={() => setCount(count + 1)} />;
}
```

Совместный паттерн — «поднятие состояния»: state живёт в общем предке, детям раздаются props (данные) и колбэки (события). Данные текут вниз, события — вверх.

## Что такое поднятие состояния (lifting state up)?

Когда два компонента зависят от одних данных, состояние перемещается к ближайшему общему предку, а вниз идёт через props.

```tsx
function Calculator() {
  const [value, setValue] = useState("");
  return (
    <>
      <Celsius value={value} onChange={setValue} />
      <Fahrenheit value={value} onChange={setValue} />
    </>
  );
}
```

Минус — «пропс-дриллинг» на глубоких деревьях: лечится композицией (children), контекстом или выносом состояния в стор/серверный кеш.

## Чем серверное состояние отличается от клиентского?

Клиентское состояние — живёт в браузере, синхронно, источник истины сам UI (открытая вкладка, тема). Серверное — кеш данных с бэкенда: устаревает, может быть невалидным, загружается асинхронно, общее для сессий.

```tsx
// Клиентское: UI-флаг
const [modalOpen, setModalOpen] = useState(false);

// Серверное: данные — responsibility кеш-слоя
const { data } = useQuery({ queryKey: ["users"], queryFn: fetchUsers });
```

Библиотеки типа React Query/SWR созданы именно для серверного состояния: кеш, дедупликация, рефетч, инвалидация — всё не нужно тащить в Redux.

## Когда использовать Context, а когда Redux/Zustand?

Контекст — редкие, глобальные, медленно меняющиеся значения (тема, локаль, user). Сторы (Redux, Zustand) — высокочастотные обновления и сложные сценарии: подписка селекторами ре-рендерит только заинтересованных.

```tsx
// Zustand: подписка на срез состояния
const count = useStore((s) => s.count); // ре-рендер только при изменении count
```

Правило: контекст меняет значение → ре-рендер всех потребителей. Для состояния вроде корзины, фильтров, счётчиков — стор с селекторами; для конфигурации и DI — контекст.

## Как управлять формами: контролируемый ввод vs библиотеки?

Простая форма — локальный `useState` на каждое поле или один объект-стейт. Сложная (валидация, вложенные поля, массивы, dirty/touched) — react-hook-form/Formik: они держат значения вне рендера и ре-рендерят меньше.

```tsx
// react-hook-form: неконтролируемый по умолчанию
const { register, handleSubmit, formState: { errors } } = useForm();
<input {...register("email", { required: true })} />
```

Бонус: интеграция со схемами (zod) — одна декларация и для типов, и для рантайм-валидации.

## Как загружать данные: useEffect + fetch vs специализированные хуки?

Классика с подводными камнями: `useEffect` + `fetch` требует вручную обрабатывать гонки, отмену, кеш и ошибки.

```tsx
// ⚠️ Гонка: быстрый ответ старого запроса может прийти последним
useEffect(() => {
  let cancelled = false;
  fetchUsers().then((data) => { if (!cancelled) setUsers(data); });
  return () => { cancelled = true; };
}, [query]);

// ✅ С React Query — кеш, отмена, retry из коробки
const { data, isPending, error } = useQuery({
  queryKey: ["users", query],
  queryFn: () => fetchUsers(query),
});
```

Загрузка в эффекте оправдана для простых случаев; для production-грид данных — кеш-библиотека или SSR-загрузка (Server Components).

## Что такое составное состояние и как его не рассинхронизировать?

Несколько `useState`, зависящих друг от друга, могут попасть в невозможные комбинации («loading: false, data: null, error: null»). Решение — один state-автомат.

```tsx
// ❌ три независимых useState
const [loading, setLoading] = useState(false);
const [data, setData] = useState(null);
const [error, setError] = useState(null);

// ✅ одно состояние с дискриминантом
type State =
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; error: string };
```

Также помогает `useReducer`: переходы описаны явно, промежуточные состояния невозможны by design.

## Как передавать данные «вниз» без пропс-дриллинга?

Инструменты: композиция через `children` (компонент-обёртка не знает содержимого), контекст для сквозных зависимостей, вынос состояния наружу (стор или URL-параметры).

```tsx
// Композиция вместо проброса onSelect пять этажей вниз
<Card actions={<button onClick={handleSave}>Сохранить</button>}>
  <CardContent />
</Card>
```

Фильтры/пагинация/поиск уместно держать в URL — состояние разделяемо ссылкой и переживёт F5.
